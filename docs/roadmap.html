Foresight Build Roadmap

The steps from the V5 vision document to a launched, multi-tenant SaaS: a micro-frontend web app with a login, a role-permission matrix, working-calendar forecasting, dashboards and seat-based billing — built in Next.js, English and Arabic from day one.

Phase 0 is already done in the accompanying repository: the monorepo, the three Next.js zones, the design system, the RBAC and forecasting kernels with tests, and a clickable prototype that shares the same screen components as the real app. Everything after that is sequenced so that each phase ships something a customer can use, and so that billing (Phase 5) lands before public launch rather than after it.

Architecture: micro-frontends on Next.js Multi-Zones

Each business capability is its own deployable Next.js application ("zone"). The shell owns the root path and authentication and proxies every other prefix to the zone that owns it. Zones share a thin kernel of packages — UI, RBAC, forecasting, i18n — so they look and behave as one product while being built, tested and deployed independently. Crossing a zone boundary is a full page navigation on purpose; inside a zone navigation is client-side.

Why zones instead of one app

Independent deploys and ownership per capability (billing can ship without redeploying the task board), smaller build graphs, and a clean path to add zones for integrations, reporting and admin. It is the officially supported micro-frontend model for Next.js, so no custom module-federation runtime to maintain.

What stays shared

The design system and every screen (@ptp/ui), the permission matrix (@ptp/rbac), the calendar math (@ptp/forecast), translations, and the host adapter. A zone is a layout plus ~40 lines of pages. Kernel changes are versioned through the workspace, so a zone opts into an upgrade by rebuilding.

Backend shape

Start with server components + route handlers per zone talking to one PostgreSQL through Prisma (a modular monolith). Long-running work — forecast snapshots, alerts, Stripe webhooks — runs in queue workers. Split services out only when a zone's load or team justifies it.

Tenancy

Every tenant-owned row carries organizationId; Prisma client extensions inject the filter so a query cannot forget it. Enterprise "dedicated server" is the same code with a dedicated database and workers, deployed by Helm chart.

Roles & permissions

One matrix, defined once in @ptp/rbac, is used three ways: assertCan() in every route handler and server action, can() to show or hide controls in the UI, and the "Roles & permissions" screen that renders the matrix itself. Organization roles govern billing and membership; project roles govern everything inside a project. Custom roles (Business/Enterprise) are stored as a permission set per organization and evaluated by the same function.

Forecast engine

The seven formulas of §5.1 are implemented in @ptp/forecast as pure functions over a working calendar, so the same code runs in the browser (live "what if I set 40 %?" on the task page) and in the nightly worker. The unit tests reproduce the §5.2 example exactly:

Sun–Thu calendar · start Sun 6 Sep · due Thu 17 Sep · as of Thu 10 Sep · 25 % done
PWD 10  →  PV 10 %/day  →  AWDE 5  →  WD-AV 5 %/day
REWD (100 − 25) / 5 = 15 working days  →  FCD Thu 1 Oct (3 calendar weeks)
WD-DV = +10 working days  →  health: DELAYED  →  high-priority alert to PM + assignee

In production the worker writes a ForecastSnapshot per task per day (and immediately on any progress update), and dashboards read snapshots rather than recomputing on request — that is what keeps "thousands of concurrent tasks" (§4.3) cheap. Alert rules: red when WD-DV > 2 working days, amber when 0 < WD-DV ≤ 2 or actual velocity drops below 85 % of planned; alerts are de-duplicated per task per day and per channel.

Work management core

  • Projects CRUD with metadata, archive, baseline milestones; working-calendar templates (Sun–Thu, Mon–Fri) and custom calendars with holiday sets and per-user leave.
  • Tasks and subtasks with priority, planned days/hours, baseline dates, tags, FS/SS dependencies, restricted visibility; six-state lifecycle with review hand-off.

  • Board and list views with filters; optimistic updates; keyboard accessibility audit.

Gate: a pilot team runs one real two-week project entirely in the product.

3

Forecast engine in production

3 weeks · snapshot jobs, alert rules, channels

  • BullMQ worker: nightly snapshot per organization timezone plus on-change recompute; snapshot table backfill and retention policy.
  • Alert rules with thresholds per plan (email only on Starter; Slack/Teams on Pro+); de-duplication and quiet hours.
  • Critical path from FS/SS dependencies; project-level FCD derived from the critical path rather than the worst task.
  • Forecast accuracy metric: predicted FCD vs actual completion, shown on the dashboard.

Gate: alerts fire correctly for a seeded set of 5,000 tasks within the nightly window.

Timeline

Security & scale (§4.3)

Encryption

TLS 1.3 at the edge, AES-256 at rest for the database, object storage and backups; secrets in a managed vault; field-level encryption for SSO metadata and API keys.

Tenancy & access

Row-level organizationId scoping injected by the ORM; assertCan() on every mutation; short-lived sessions; audit trail on all role changes.

Availability

Stateless zones behind a CDN, multi-AZ database with point-in-time recovery, queue retries with idempotent jobs, health checks per zone, status page. Target 99.9 % (99.99 % for dedicated Enterprise).

Scale

Forecasts are precomputed snapshots, not request-time math; dashboards read materialised views; snapshot jobs shard by organization so thousands of concurrent tasks stay within the nightly window.

Compliance readiness

SOC 2 controls tracked from Phase 1 (access reviews, change management, incident response); data export/delete for GDPR; regional data residency via the dedicated-deployment path.

Accessibility & i18n

WCAG AA contrast, keyboard paths and focus states baked into the primitives; Arabic RTL with logical properties; date and number formatting deterministic across server and client.
